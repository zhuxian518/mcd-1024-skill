# 产品需求：从「吃什么」到可确认的一个选择

状态：概念方案，AI 协作制作。现有执行依据为 [Skill](../../SKILL.md) 与 [MCP 集成说明](../../MCP_INTEGRATION.md)，本 PRD 不改变它们；方案中的界面、自动校验和埋点不代表生产已实现。

## 1. 问题与待验证假设

目标情境：用户在固定预算与口味/营养约束下，希望快速决定一餐。现有菜单、券和营养信息分散，可能造成反复比较；这是待访谈和观察验证的问题假设，不是已有用户研究结论。

- H1：唯一主推荐加简短理由，比直接展示长列表更利于做决定。验证需比较相同任务下的决策完成率与耗时。
- H2：展示预算、营养数据来源和核价时间能帮助用户理解推荐。验证需检查用户是否正确理解价格及未知项。
- H3：提交前单独复核，能降低把「想看看」误当成交易授权的风险。需用误触与条件变化任务验证。

不假设使用频率、留存、转化或节省金额已有提升。营养目标只用于数据筛选，不能将一般营养数值当作医疗建议。

## 2. 用户旅程与范围

| 阶段 | 用户任务 | 系统责任 | 结果/退出 |
|---|---|---|---|
| 提出需求 | 填预算、偏好、蛋白目标 | 澄清门店/餐段等缺项，校验输入 | 可修改，不能先消费 |
| 生成建议 | 看一个选择是否满足约束 | 门店 → 菜单 → 营养 → 券 → 核价 | 理由、约束、未知项 |
| 复核 | 确认门店、商品、金额与操作 | 展示完整摘要，变化后重新确认 | 可返回或退出 |
| 明确授权 | 同意具体写操作 | 仅在授权范围调用工具 | 成功、失败或待核验 |
| 收尾 | 看结果或取消 | 查结果；成功才记订单 | 未知状态不盲重试 |

| 优先级 | 产品需求 | 本目录覆盖 |
|---|---|---|
| P0 | 预算/偏好/营养输入、可解释推荐、预算硬约束 | 合成规则演示 |
| P0 | 门店/价格复核、明确授权、复核前可退出 | 模拟确认，无实际写操作 |
| P0 | 无解、接口失败、价格变化、写入结果不明 | HTML 可点击场景或评测用例 |
| P1 | 「老朋友/尝个新」、冷启动说明 | 现有 Skill 已有指令；HTML仅显示模拟备选 |
| P1 | 真实成功后本地记忆、注明日期的指数 | 真实 Skill 范围；HTML不存储、不采样 |
| P2 | GUI账户连接、订单后端、支付/通知/埋点平台 | 不在本案例实现范围 |

HTML 不复刻完整菜单或所有 MCP 工具。它只证明界面路径可以讨论和测试；生产推荐排序、工具参数、账户权限仍由宿主和服务定义。

## 3. 状态、权限与异常

正常状态：编辑需求 → 生成候选 → 查看推荐 → 复核摘要 → 勾选理解模拟性质 → 模拟提交 → 演示完成。修改需求重新生成会清除旧确认；不会沿用旧金额授权。

生产流程要求与原型对应：

| 场景 | 生产需求 | 原型/评测方式 |
|---|---|---|
| 非法预算或目标 | 不发工具请求，指出输入范围 | HTML原生表单校验 |
| 约束无解 | 显示最接近方案及具体缺口，不伪称满足 | 合成预算/蛋白筛选 |
| 未连接/鉴权失败/缺工具 | 报告失败步骤，检查宿主权限，禁止编造实价 | 「接口失败」场景；未调用服务 |
| 门店打烊/餐段不可售 | 选营业门店或接口支持的预约时段 | 用例走查；HTML不假装预约 |
| 营养缺项 | 标记未知，不能通过硬约束 | 用例走查 |
| 核价变化 | 展示新旧价格，旧确认失效；超预算则停止 | 「核价变化」场景 |
| 写操作结果不明 | 先查询状态，不自动重复创建订单 | 「结果不明」场景，无重试提交按钮 |
| 确认前退出 | 不触发写操作，回到需求编辑 | 可点击「暂不继续」 |
| 已创建订单后取消 | 明确订单与影响，单独授权 `cancel-order` | 仅在用例中审阅，不把原型退出当作取消订单 |
| 本地保存失败 | 保留原文件并说明未记住，勿重复消费 | 用例走查 |

`auto-bind-coupons`、`create-order`、`cancel-order` 均为需逐项确认的写操作；不能把推荐表达或页面访问当授权。生产操作具体参数以工具 schema 为准。原型按钮只改变页面文本，不调用这些工具。

## 4. 数据与技术边界

[架构图](architecture.svg) 区分用户、宿主、Markdown Skill、本地 JSON 与官方服务。Skill 是指令，宿主负责执行和凭据注入，官方 MCP 承担账户操作。Token 不应进入产品文档、日志或原型；个人记忆与订单不提交公共仓库。JSON 在本地不代表宿主模型处理全程离线。

原型只含固定合成菜单，在内存中处理预算与偏好；无外链、无网络请求、无存储、无账户标识。合成数值不可用于真实食品的价格或营养声明。渲染动态值用 `textContent`，不用用户输入拼 HTML。

## 5. 验收与目标

| 编号 | 可验收条件 | 验证方式 |
|---|---|---|
| A1 | 输入合法且有解时，主方案金额≤预算，蛋白≥目标，满足所选口味 | 合成用例逐项比对 |
| A2 | 无解时明确约束缺口，无法进入确认 | 低预算/高蛋白任务 |
| A3 | 推荐页不直接产生写操作，复核摘要可返回，须再次主动确认 | 状态与事件走查 |
| A4 | 失败、价格变化、结果不明均有明确反馈且不会静默提交 | 异常用例 |
| A5 | 每个价格/营养值所在界面可见合成标识，无「真实下单成功」表述 | 页面审查 |
| A6 | 键盘能完成输入、推荐、复核、退出；窄屏无水平溢出 | 浏览器走查 |
| A7 | 架构与文档不把概念GUI、宿主和官方服务混为一体 | 交叉审查 |

目标：合成测试中预算越界、未经确认写操作、假称真实数据三类关键错误均为 0；失败用例预期路径覆盖率 100%。这些是门槛目标，并非已经取得的实测结果。真实用户决策完成率/耗时目标应在建立基线后另行设定，不虚设提升百分比。详细口径与未运行状态见 [EVALUATION.md](EVALUATION.md)。
